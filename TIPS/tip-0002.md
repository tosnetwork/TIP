# TIP-0002: Post-Quantum Validator Consensus from Genesis

## Abstract

This TIP specifies **post-quantum validator consensus at Genesis, minimal
cryptographic agility, and resource budgets as the binding constraint on
validator scale**.

The post-quantum (PQ) boundary is deliberately narrow. Every authority that can
produce or finalize a block, enter the validator set, vote as a validator, or
change consensus-critical configuration MUST use ML-DSA-44 from the first
mainnet block. Ordinary user wallets and network transport identity remain
Ed25519 by default.

There is no classical era, no migration phase, no hybrid authorization, no
per-validator algorithm negotiation, and no fallback path. Genesis activates
exactly one consensus PQ algorithm; an unknown algorithm identifier fails
closed.

The proposal separates three identities that earlier drafts conflated: a stable
32-byte `validator_id`, a 32-byte `key_id` derived from the PQ key, and the
variable-length PQ public key itself. Key rotation changes `key_id` while
`validator_id` survives; both are bound into the validator-set commitment and
the consensus session identity.

Validator committee size is governed by declared byte and verification budgets
rather than a hard-coded number. The launch target is 21 active masterchain
validators with a 100 `max_main_validators` ceiling, and a configuration that
exceeds the PQ resource envelope MUST be rejected before it becomes
authoritative, not after.

This TIP freezes the identity model, the signature domains, the encoding
requirements, the authority boundary, and the acceptance gates. It does not
activate anything by being merged.

## Motivation

Validator signatures authorize consensus decisions. A quantum-capable adversary
that can forge them can forge finality, install a validator set, or rewrite
consensus-critical configuration. That is a different problem from wallet key
security, and it has a different deadline: a chain cannot retroactively make an
already-finalized classical history unforgeable.

TOS has not launched mainnet. This is the one moment at which PQ validator
consensus costs a specification and an implementation rather than a migration.
A migration of a live chain requires era boundaries, dual-authorization
windows, trusted transition checkpoints, and a long period during which a
classical key remains an alternate path to consensus authority. None of that is
necessary if the chain never has a classical era.

The narrow boundary is what makes this affordable. Converting the whole key and
networking stack would turn a scoped consensus change into a rewrite of TOS.
The scope is therefore:

```text
Validator consensus / finality / validator governance -> ML-DSA-44
Ordinary user wallets                                 -> Ed25519 by default
Network transport identity (ADNL/DHT/Overlay/QUIC)    -> Ed25519
```

The base already supports this. At the reviewed baseline `tosnetwork/tos`
commit `2004ce5e618c4a9d8ed5fe5ae51912d65bb524cd`, TOS ships an ML-DSA-44
verifier in `crypto/pq`, a `PQCHECKSIG_MLDSA44` VM primitive with FunC/Tolk
bindings, and Simplex candidate/vote signatures that are already carried as
variable-length `bytes`. What remains classical are the consensus *interfaces*:
`ValidatorDescr.key` is an `Ed25519_PublicKey`, `block.tlb` fixes
`ed25519_signature#5`, `signature-set.cpp` assumes 64-byte signatures, the Rust
codec fixes `SigPubKey([u8;32])`/`CryptoSignature([u8;64])`, and
`elector-code.fc` / `config-code.fc` authorize with a 256-bit key and a 512-bit
signature.

Feasibility was measured before this direction was adopted rather than
asserted. A real ML-DSA-44 verify loop over a real signed vector on a
single-threaded development host measured **294.6 microseconds per
verification**, which places a 100-signer certificate at roughly 29.5 ms of
sequential verification and 242,000 bytes — 0.18% of a 16-second round attempt
and 5.8% of the 4 MiB block limit. Even the 400-validator protocol maximum sits
at 0.74% of a round. The classical-era, aggregation-dependent designs that a
migration would have forced are not required for feasibility at TOS launch
scale. These numbers are a single-host, verify-only feasibility gate; Section 14
requires them to be re-measured on multi-node hardware before Genesis
parameters are frozen.

## Normative language and maturity

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT,
RECOMMENDED, MAY, and OPTIONAL are to be interpreted as described in RFC 2119
and RFC 8174. [9]

Publication or merger of this Draft changes no software. Structures shown below
are **logical models, not wire schemas**: no implementation may infer
constructor numbers, field widths, or serialization from an illustrative name.
The implementation freezes the exact encodings, and Section 15 states which
evidence must exist before each boundary is considered closed.

Where this document states a provisional value — the launch committee size, the
`ConfigParam 16` ceilings, the certificate budget — it is a launch candidate
that the measurement work in Section 14 confirms or replaces. Where it states
an authority rule, that rule is not negotiable by a parameter.

## Specification

### 1. Authority boundary

The following authorities are consensus-critical. Each MUST verify under
ML-DSA-44 at Genesis, or MUST NOT exist:

```text
validator proposal signing
validator notarize / finalize / skip votes
consensus certificates
BlockSignatures / BlockProof finality
validator election authorization
validator configuration / governance votes
any unilateral admin authority able to replace the ValidatorSet
any unilateral admin authority able to replace elector or config code
```

No Ed25519 key may remain an alternate path to obtain, exercise, delegate, or
mutate any authority in that list. This is a property of the launched system,
not of one verification function: an implementation that verifies PQ finality
correctly while leaving a classical administrative path able to replace the
validator set has not implemented this TIP.

### 2. Wallet and transport boundary

Ordinary Wallet, Wallet V5, and Agent Wallet user authorization remains Ed25519
by default. Wallet address derivation is unchanged. No user is required to
migrate funds, no wallet key is replaced, no dual signing is introduced, and no
wallet-era fallback logic exists to be introduced.

The existing optional `PQCHECKSIG_MLDSA44` capability remains available to
accounts that choose it. That is an application choice, not a dependency of
this proposal.

Transport identity remains Ed25519 across ADNL, DHT, Overlay, and QUIC.
Transport identity and consensus authority are separate security domains. An
Ed25519 network or temp key MAY identify and connect a validator node. It MUST
NOT, alone or in combination with other classical keys:

- make the node a consensus validator;
- authorize finality;
- authorize validator election or governance;
- rotate the PQ consensus key; or
- mutate the authoritative validator set.

This TIP makes no claim of PQ confidentiality or PQ transport authentication. A
compromised transport identity remains an availability, eclipse, and
impersonation concern, analyzed separately, and bounded by the rule above.

A future wallet-security proposal may make PQ wallets default or mandatory
without changing anything specified here.

### 3. Identity model

Three identities are distinct and MUST NOT be conflated:

```text
validator_id  = 32 bytes, stable across PQ key rotation
key_id        = 32 bytes, changes when the PQ consensus key changes
public_key    = variable length, suite-defined (1312 bytes for ML-DSA-44)
```

`validator_id` is the membership identity. The initial source is the
validator's masterchain staking/controller account identifier:

```text
validator_id = controller_account_id   // 256-bit masterchain account id
```

The elector already authenticates the source account of a stake operation, so
this yields a stable identity without introducing a separate registry.

`key_id` is the consensus signing-key identity, derived as:

```text
key_id = SHA-256(
    "TOS-PQ-CONSENSUS-KEY-v1"   // exact ASCII, no separator, no NUL
    || u16_le(algorithm_id)     // exactly 2 bytes, little-endian
    || public_key               // raw suite-length key, no length prefix
)
```

This encoding is normative and frozen. Derivation **fails closed**: an
algorithm identifier that is not the admitted consensus suite, or a public key
whose length is not exactly the suite length, yields no `key_id` at all, so an
unadmitted suite can never acquire a usable consensus identity.

The frozen reference vector, reproducible with any SHA-256 implementation, is:

```text
SHA-256("TOS-PQ-CONSENSUS-KEY-v1" || u16_le(1) || 0x01 * 1312)
  = abf4e6dde7107b53a48ab9b70fc3942245146d9e3747eb2f5f1aa734b04e1411
```

A stored `key_id` that does not equal the derivation from the stored
`(algorithm_id, public_key)` MUST be rejected as a parse error. The stored value
is never the authority for the derived one.

Large PQ public keys are never user-facing identities and are never truncated
into one. Block producer identity, membership lookup, and operator-facing
addressing use `validator_id`.

### 4. Consensus PQ types

The type surface is deliberately small:

```text
PQAlgorithmId
PQBytes
ConsensusPQKey
ConsensusPQSignature
PQValidatorDescr
PQConsensusLimits
```

Logically:

```text
ConsensusPQKey {
    algorithm_id
    key_id       : 32 bytes
    public_key   : PQBytes
}

ConsensusPQSignature {
    algorithm_id
    signature    : PQBytes
}

PQValidatorDescr {
    validator_id : 32 bytes
    consensus_key: ConsensusPQKey
    weight
    adnl_addr    : 32 bytes
}

PQConsensusLimits {
    algorithm_id
    public_key_bytes
    signature_bytes
    max_certificate_bytes
    max_certificate_signers
    verification_budget
}
```

Genesis activates exactly one consensus PQ algorithm. The launch suite is
ML-DSA-44 as standardized by FIPS 204 [7]:

| Suite property | Value |
|---|---:|
| public key | 1312 bytes |
| signature | 2420 bytes |

An unknown `algorithm_id` fails closed everywhere it appears: descriptor
parsing, `key_id` derivation, signature verification, and configuration
admission. There is no negotiation, no "best supported suite", and no
simultaneous multi-algorithm validator consensus at launch. Replacing the suite
later is an explicit protocol upgrade with its own proposal, not a runtime
selection.

### 5. Canonical PQBytes

ML-DSA-44 keys and signatures exceed one cell and exceed the existing
1024-byte `CellString` bound, so the implementation MUST define one canonical
bounded byte codec with:

- an explicit byte length;
- a fixed canonical partition and tree shape, with a balanced tree preferred
  over an unnecessarily deep chain;
- no alternate encoding of the same byte string;
- an exact upper bound checked **before** allocation or traversal;
- exact decoding, rejecting trailing bits and trailing references; and
- byte-identical C++ and Rust implementations locked by shared vectors.

Suite validation additionally requires the exact ML-DSA-44 lengths, 1312 and
2420, even where the structural ceiling of the codec is larger. A structural
bound is not a suite bound, and neither substitutes for the other.

This codec is new and minimal. Earlier `AuthBytes`-style layered encodings from
the abandoned validator-authority design MUST NOT be reintroduced.

### 6. Validator descriptor and validator set

A PQ validator descriptor carries `validator_id`, `algorithm_id`, `key_id`,
`public_key`, `weight`, and `adnl_addr`, encoded under a new descriptor
constructor. The implementation freezes the accepted descriptor tag set;
read-side leniency across implementations MUST be removed before the new format
lands, and C++ and Rust MUST accept exactly the same constructor set.

`adnl_addr` is explicit, mandatory, and non-zero. It is never derived from the
PQ consensus key.

Validator-set parsing MUST reject, as ordinary parse or configuration errors
rather than process-aborting assertions:

- duplicate `validator_id`;
- duplicate `key_id`;
- `key_id` inconsistent with `(algorithm_id, public_key)`;
- unknown `algorithm_id`;
- wrong public-key length for the suite;
- zero or missing ADNL identity;
- invalid `validator_id` where the format forbids it; and
- invalid weight or weight accumulation under the existing validator-set rules.

Membership lookup keys on `validator_id`. Key-identity uniqueness is enforced
on a separate path so that a duplicate `key_id` and a duplicate membership
identity are rejected without conflating the two.

A duplicate consensus public key is already rejected by the duplicate `key_id`
rule, because `key_id` is a function of the key and the stored value is checked
against the derivation. An implementation that also compares public keys
directly MUST construct the input that trips that comparison alone; if it
cannot, the check is redundant and MUST NOT be counted as independent
protection.

Block `created_by` becomes the stable `validator_id`. This conversion is
end-to-end across producer identity, candidate construction, candidate
persistence, collator-node request paths, and non-final candidate queries. No
code may manufacture an Ed25519 public key from a `validator_id` to satisfy an
older interface. Transport source and peer identity remain separate fields.

### 7. Commitments: validator set and session

Both commitments bind stable identity and current key. Neither may be
recomputed from a sender-supplied value.

The validator-set commitment uses a new magic — the inherited preimage magic
MUST NOT be reused for a different preimage — over exactly:

```text
magic
cc_seqno
validator_count
for each validator, in canonical order:
    validator_id : 32 bytes
    key_id       : 32 bytes
    weight       : uint64
    adnl_addr    : 32 bytes
```

`key_id` already binds `algorithm_id` and the public key, so the 1312-byte key
is not duplicated in the short-hash preimage. The exact preimage bytes and
resulting hash are locked in cross-language vectors, and the independent Rust
implementation changes in the same commit as the C++ one.

Consensus session identity commits to at least `validator_id`, `key_id`,
`adnl_id`, and `weight` per member. The existing Ed25519 group-member form
cannot represent both frozen identities, so a PQ member form is added within
the same result type.

The required invariant, stated as negatives an implementation must demonstrate:

- the same `validator_id` with a different `key_id` produces a different set
  commitment and a different session identity;
- the same `key_id` with a different `validator_id` produces a different
  session identity; and
- legacy Ed25519 member bytes cannot be silently interpreted as PQ member
  bytes.

Genesis and zerostate hashes change as a result. That is expected and
acceptable before launch.

### 8. Signature domain separation

ML-DSA signing under FIPS 204 takes an explicit context. Exactly four contexts
are frozen, one per authority surface, as exact ASCII:

```text
"TOS-CONSENSUS-SIMPLEX-v1"
"TOS-VALIDATOR-ELECTION-v1"
"TOS-VALIDATOR-CONFIG-VOTE-v1"
"TOS-CONFIG-ADMIN-v1"
```

All four are defined in code at the primitive boundary so that later work
cannot invent a fifth domain informally; adding one is a consensus format
change. A signature produced under one context MUST NOT verify under another,
and that property MUST be asserted directly against all four surfaces rather
than assumed from the construction.

Within the Simplex surface, proposal, notarize, finalize, and skip remain
separated by their existing constructors inside the existing signed-data
preimage. This TIP adds no duty hierarchy, no role-key hierarchy, and no
per-vote key derivation.

### 9. Simplex proposals, votes, and certificates

Simplex semantics are unchanged. Only the authentication primitive and the
identity plumbing change:

- proposal signing and verification use the PQ consensus key;
- notarize, finalize, and skip signing and verification use the PQ consensus
  key;
- certificate verification uses the PQ consensus key;
- quorum rule, weights, sender/index binding, session, slot, candidate, and
  vote constructors are semantically unchanged.

The peer-validator structure carries stable `validator_id`, the
`ConsensusPQKey`, the ADNL identity, and weight, instead of treating one
generic Ed25519 public key as both identity and verifier.

For a well-formed certificate, a validator contributes its recorded weight once
and only after its signature verifies against the key bound by the authoritative
set. Duplicate signers, unknown signers, wrong `key_id`, mismatched statement,
and invalid signatures are rejected. Weight comes from the authenticated
validator set, never from the sender.

The quorum predicate is unchanged from the baseline. For a nonempty valid set
with total weight `W` and distinct authenticated signer weight `S`:

```text
3 * S >= 2 * W
```

Arithmetic MUST remain checked or widened and MUST preserve the existing weight
bounds. A readiness or participation percentage is an operational observation,
never a quorum denominator.

Persisted and rebroadcast signatures are the exact bytes already produced. A
failed PQ verification is never reinterpreted as a classical signature, and a
restart never causes a node to sign classically.

### 10. Block signatures, proofs, and light verification

The historical Ed25519 block-signature constructors MUST NOT be reinterpreted
as PQ. One explicit PQ-native block-signature constructor is allocated, with a
canonical signature-pair representation carrying:

```text
validator_id
algorithm_id
signature : PQBytes
```

The trusted validator set supplies the key and `key_id`; the set commitment and
session identity already bind it, so the pair does not restate the public key.

A PQ mainnet accepts the PQ constructor from Genesis. There is no runtime era
selection and no try-PQ-then-legacy fallback. Historical Ed25519 constructors
MAY remain in offline tooling and tests; they are not an accepted mainnet
finality format.

Light-client verification stays simple:

```text
trusted key block / state
  -> PQ validator set
  -> PQ block signature set
  -> weighted quorum verification
```

No authority registry, key-birth reconstruction, policy proof, or multi-root
mechanism is introduced. Certificate hard byte and count bounds are enforced
before expensive cryptography, on the light path as well as the full path.

### 11. Election and consensus-critical governance

Validator election stops using a 256-bit key with a 512-bit signature. The
election path binds:

```text
controller / source account -> validator_id
validator_id                -> current PQ consensus key
PQ signature                -> the exact election request
```

The elected validator-set configuration contains PQ descriptors. Validator
configuration votes authorized by the validator set verify against the
validator's PQ consensus key.

These paths execute in the elector and configuration contracts and therefore
use the `PQCHECKSIG_MLDSA44` VM primitive, which is gated by global version 16.
**Global version 16 is therefore a mainnet prerequisite for the complete PQ
authority boundary even though ordinary wallets remain Ed25519.**

The configuration contract's separate classical master/admin external signature
path can today change configuration and upgrade configuration and elector code.
A PQ-native mainnet MUST NOT retain that as a quantum-vulnerable unilateral
authority. Exactly one of the following MUST be chosen before launch:

```text
A. convert the configuration master/admin authorization to ML-DSA-44; or
B. remove that unilateral admin authority at Genesis and rely on the approved
   governance path.
```

There is no option under which an Ed25519 key retains the ability to replace
the validator set, the configuration contract code, or the elector code. This
is the removal of a classical governance bypass, not the introduction of an
authority framework.

### 12. Local membership and key custody

Local consensus membership MUST come from locally configured PQ custody:

```text
validator_id -> consensus PQ key
```

matched against the authoritative validator set by `validator_id`, with the
installed key and `key_id` matching that descriptor before the node may sign.
Discovering membership by enumerating installed Ed25519 temp keys MUST stop
being the membership authority.

Ed25519 temp, permanent, and network keys MAY remain installed for network and
operator duties. Possessing them, with no matching PQ validator identity and
key, MUST leave validation participation disabled. That negative is a required
test, not an inference.

The PQ signer is a separate, narrow interface from the ADNL keyring. The
consensus verifier build stays verify-only and deterministic; key generation
and signing live in a separate target or adapter over the same pinned backend.

### 13. Resource budgets and validator scale

21 validators is a launch size, not a protocol maximum. The binding constraint
is resource usage, expressed as declared limits per active suite:

```text
max_public_key_bytes
max_signature_bytes
max_certificate_bytes
max_certificate_signers
verification work / time budget
```

The existing `ConfigParam 16` continues to carry `max_validators`,
`max_main_validators`, and `min_validators`.

Two layers apply. Structural parser bounds are enforced by the codec and the
signature-set verifier. Operating limits are selected within those bounds from
measurement.

A configuration that violates the PQ resource envelope MUST be rejected **at
admission**, before it becomes authoritative:

```text
max_main_validators <= max_certificate_signers

worst_case_certificate_bytes(max_main_validators) <= max_certificate_bytes
```

Accepting such a configuration into chain state and having nodes refuse it
afterwards can halt the network, so node-side rejection alone is insufficient.
Nodes independently apply the same deterministic rule when reading
configuration; the two checks are the same rule enforced at two points, not two
sources of truth.

Performance policy that cannot be evaluated deterministically inside the
contract is converted into a conservative signer-count or byte ceiling. Raising
that ceiling later is an explicit protocol upgrade.

An implementation MUST NOT trim validators, ignore surplus signatures, silently
lower a quorum, or fall back to a classical suite in order to fit a budget.

### 14. Genesis parameters

Provisional launch direction, to be confirmed or replaced by the measurements
below:

```text
active masterchain validators = 21
max_main_validators           = 100
max_validators                = 400
min_validators                = 4

consensus PQ suite            = ML-DSA-44
public key                    = 1312 bytes
signature                     = 2420 bytes
global version                = 16
```

Before these are frozen, multi-node measurements MUST be taken with the actual
implementation at 21, 32, 64, and 100 validators, recording at least: validator
set and PQ key state size; single signature size; full certificate size;
proposal and vote network size; certificate verification p50/p95/p99; proposal
and vote propagation latency; block and finality proof size; CPU; memory; and
light-proof size and verification latency.

The single-host feasibility gate quoted in the Motivation is a direction check,
not the parameter evidence. The frozen Genesis parameters are documented from
the multi-node results.

### 15. Delivery boundaries and gates

| Boundary | Work to implement and audit |
|---|---|
| PQ primitive, canonical byte codec, signer and key store | suite lengths, `key_id` derivation, fail-closed unknown suite, frozen contexts, structural bounds |
| Validator descriptor, validator set, identity and commitments | descriptor encoding, uniqueness rejections, set-commitment v2, session member form, `created_by` conversion, local membership custody |
| Election and configuration governance | PQ election binding, PQ configuration votes, global version 16, classical admin path converted or removed |
| Simplex proposal, vote, and certificate authentication | PQ signing and verification, unchanged quorum and session semantics, no classical reinterpretation |
| Block signatures, proofs, full node and light verification | PQ constructor, codec parity, bounds before cryptography, rejection of classical finality format |
| Resource budgets and network measurement | multi-node measurement, admission-time configuration rejection, frozen Genesis parameters |

Each boundary closes on evidence, not on a checklist entry:

1. Independent known-answer vectors for ML-DSA-44, plus a production
   signer verified against the production verifier.
2. Byte-exact cross-language vectors for every consensus-visible encoding and
   hash preimage, produced by C++, Rust, and — once it produces PQ validator
   state — the contract side.
3. Size controls immediately outside every exact bound: 1311/1312/1313 for the
   public key, 2419/2420/2421 for the signature, and the maximum and
   maximum-plus-one for certificate bytes and signer count.
4. Context-substitution refusal asserted across all four frozen domains.
5. Negative tests for every rejection in Section 6, each with an otherwise
   valid input that trips exactly that guard.
6. A demonstration that an Ed25519 temp, permanent, or network key alone cannot
   activate consensus membership, authorize finality, or authorize election.
7. Multi-node runs at 21, 32, 64, and 100 validators, with the recorded
   measurements of Section 14.
8. An over-budget `ConfigParam 16` proposal rejected before installation, and
   independently refused by a node reading configuration.

**Every guard above is verified by mutation: remove the guard, observe the test
fail, restore it.** A negative test that passes because the input never reached
the code under test is not evidence, and a guard whose condition is already
guaranteed elsewhere protects nothing. Release-mode assertions stay live.

## Rationale

**Why Genesis rather than a migration.** Every migration design carries an era
boundary, a period of dual authorization, a trusted transition checkpoint, and
a long window in which a classical key remains sufficient for consensus
authority. Those mechanisms are the bulk of the complexity and most of the
residual risk, and they exist only to serve a classical history that TOS does
not have yet. Launching PQ-native deletes the problem instead of managing it.

**Why the boundary is narrow.** The security claim is about the authority to
create and finalize blocks and to change who holds that authority. Wallet keys
and transport identities do not hold that authority, and converting them would
expand a scoped change into a network-wide rewrite while delaying the part that
cannot be retrofitted. Ordinary users are not asked to migrate anything.

**Why `validator_id` is not `key_id`.** Deriving membership identity from the
PQ public key would change a validator's identity on every key rotation,
propagating into stake records, block producer identity, operator tooling, and
historical attribution. Separating them keeps rotation an operational event.
The separation must not weaken binding, which is why both identities enter the
set commitment and the session identity, and why a rotated key produces a
different commitment.

**Why one suite.** Per-validator algorithm choice creates downgrade surface,
negotiation logic, and a verification matrix, in exchange for flexibility that
a pre-launch chain does not need. Minimal agility here means the `algorithm_id`
field exists and fails closed, so a future suite change is a reviewed upgrade
rather than an interface redesign — not that several suites are authoritative
at once.

**Why budgets instead of a committee constant.** A hard-coded committee size
encodes today's measurement as tomorrow's protocol rule. Declaring byte and
verification budgets makes the real constraint explicit and checkable, lets 21
be a launch choice rather than a protocol maximum, and gives configuration
admission a deterministic rule to enforce. Measurement showed the margins are
large, so the budget is a guard rail, not a limit the design is straining
against.

**Why raw signatures.** Individual ML-DSA-44 verification is fast enough at
every scale this TIP targets, and it is the simplest thing that can be
implemented, measured, and audited. Aggregation may be proposed later against
measured need; it must not be assumed necessary, and proving classical
signatures does not make them post-quantum.

**What the earlier draft got wrong.** The previous revision specified a
classical launch on extensible interfaces followed by staged onboarding, hybrid
AND-authorization, and eventual PQ enforcement, together with an authority
registry, a role-key hierarchy, and a configuration parameter to carry the
policy. That design is withdrawn in full. It optimized for a constraint TOS
does not have — a live classical mainnet — and paid for it with migration
machinery that is itself the largest source of consensus risk. The following
are explicit non-goals and MUST NOT be reintroduced:

```text
ValidatorAuth registry and its configuration parameter
staged classical / shadow / hybrid / PQ-required phases
five-role key hierarchy
signer-permit hierarchy
legacy consensus migration, era split, or fallback
simultaneous multi-algorithm validator consensus
forced PQ migration of ordinary wallets
PQ conversion of ADNL, DHT, Overlay, or QUIC
```

The abandoned branch implementing the withdrawn design is not merged, and its
informal configuration-parameter allocation is not reserved by this proposal.
Implementation starts from the then-current `main` in a new branch.

## Backwards Compatibility

There is no mainnet to be compatible with. This proposal changes consensus
interfaces relative to the inspected source baseline: validator descriptors,
validator-set commitment, session member identity, block-signature
constructors, election and configuration authorization, and block producer
identity. Testnet fixtures, genesis tooling, key material, schemas, and
configuration are regenerated before launch, and genesis and zerostate hashes
change.

Ordinary wallet authorization, wallet addresses, wallet SDK key flows, and the
transport key stack are unchanged. Existing accounts and application contracts
are unaffected except for those that deliberately use the optional PQ
verification primitive.

Historical Ed25519 block-signature constructors keep their own meaning in
offline tooling and tests and are not accepted as mainnet finality. No previously
signed bytes are reinterpreted under a new meaning.

Because there is no classical era, no client needs an era-selection rule. A
client that cannot verify ML-DSA-44 cannot validate TOS finality and MUST fail
closed rather than report partial validation.

## Test Cases

### Included consensus model

[`../assets/tip-0002/pq-consensus-cases.json`](../assets/tip-0002/pq-consensus-cases.json)
contains input/expected-output cases for certificate acceptance and for
configuration admission.
[`check-pq-consensus.py`](../assets/tip-0002/check-pq-consensus.py) is a
standard-library-only executable model of those rules:

```
python3 assets/tip-0002/check-pq-consensus.py
```

The checker recomputes the frozen `key_id` derivation of Section 3 from its
inputs, including the reference vector, so that part of the corpus is a real
computation rather than a restated constant. Everything else is a model: the
`signature_valid` fields are **supplied verification outcomes, not signatures**.
The model exercises identity binding, `key_id` consistency, uniqueness
rejections, absence of classical fallback, weighted quorum arithmetic, and
resource-budget admission. It is not a cryptographic verifier, not a TOS
consensus implementation, and not evidence of PQ performance.

The corpus is falsifiable by construction: removing any single guard from the
checker makes at least one case fail. An implementation that adds a guard must
add the case that trips it.

### Required consensus and operational cases

| Input or injected condition | Required outcome |
|---|---|
| ML-DSA-44 known-answer vectors from an independent source | Verify |
| Production signer output verified by the production verifier | Verify |
| Public key of 1311 or 1313 bytes; signature of 2419 or 2421 bytes | Reject before verification |
| Canonical byte codec: alternate shape, trailing bits, trailing refs | Reject |
| Byte codec round trip across C++ and Rust | Identical bytes and identical hashes |
| Unknown `algorithm_id` in a descriptor, signature, or configuration | Reject; no `key_id`, no fallback |
| Stored `key_id` not equal to the derivation from the stored key | Reject as a parse error |
| Duplicate `validator_id`, duplicate `key_id`, or duplicate public key in a set | Reject |
| Zero or missing ADNL identity in a PQ descriptor | Reject |
| Same `validator_id`, rotated `key_id` | Different set commitment and different session identity |
| Same `key_id`, different `validator_id` | Different session identity |
| Legacy member bytes presented as PQ member bytes | Reject; no silent reinterpretation |
| Signature valid under one frozen context, presented under another | Reject, asserted across all four domains |
| Notarize signature presented as finalize or skip authorization | Reject |
| Wrong session, slot, or candidate | Reject |
| Certificate with one surplus invalid signature | Reject the certificate |
| Duplicate signer, unknown signer, or sender-supplied weight | Reject; weight comes from the authenticated set |
| Three equal-weight validators, two authenticated signers | Accept under the unchanged `3S >= 2W` predicate |
| Certificate exceeding `max_certificate_signers` or `max_certificate_bytes` | Reject before expensive verification |
| Ed25519 signature offered where PQ authorization is required | Reject; no fallback path exists |
| Classical block-signature constructor on a PQ mainnet | Reject |
| Node holding correct ADNL and temp Ed25519 keys but no PQ validator identity | Validation participation stays disabled |
| Election request with a tampered field or wrong `key_id` | Reject |
| Configuration vote authorized only by a classical key | Reject |
| Classical admin path attempting to replace validator set, elector, or config code | Absent, or rejected as non-PQ |
| `ConfigParam 16` whose `max_main_validators` exceeds the signer budget | Reject before installation, and independently on read |
| Restart and rebroadcast after a failed PQ verification | Exact stored bytes; never a classical signature |
| Light client following a PQ finality proof to a trusted key block | Verify; reject on wrong key, validator, suite, or signature |

Cross-language byte and vector locks are required for every consensus-visible
encoding and hash preimage. Test descriptions and the included model are not
substitutes for them.

## Security Considerations

The claim is bounded: this proposal aims to make validator authorization,
finality, election, and consensus-critical governance post-quantum from
Genesis, conditional on ML-DSA-44, correct integration, key custody, and the
underlying consensus assumptions. It does not make wallets, network transport,
or application contracts quantum-safe, and does not claim PQ confidentiality.

Primary risks and where they are addressed:

- **A classical bypass surviving somewhere in the authority set.** The
  inventory in Section 1 is the security boundary; the configuration admin path
  in Section 11 and the local membership path in Section 12 are the two places
  a bypass is most likely to persist. Both require explicit negative evidence.
- **Identity confusion.** `validator_id`, `key_id`, ADNL identity, and the PQ
  public key are different values with different lifetimes. Passing one where
  another is expected is a correctness and an authority bug; Sections 3, 6, and
  7 require them to be distinguishable by type where practical and bound
  separately in commitments.
- **Encoding ambiguity.** Two implementations that accept slightly different
  byte sets are a consensus split waiting for an adversary to find it. The
  canonical codec, the frozen tag set, and cross-language vectors exist for
  this, and read-side leniency is removed before the new format lands.
- **Resource exhaustion.** PQ signatures are an order of magnitude larger than
  classical ones. Bounds are checked before allocation and before verification,
  on the light path as well as the full path, and adversarial traffic is
  benchmarked rather than only valid traffic.
- **Configuration that halts the network.** An over-budget configuration
  accepted into authoritative state and then refused by nodes is an outage.
  Section 13 requires rejection at admission as well as on read.
- **Key custody and rotation.** ML-DSA-44 is stateless, so there is no one-time
  capacity to exhaust and no leaf-reuse failure mode; that is a deliberate part
  of the suite choice. Rotation remains an authenticated operation that changes
  `key_id`, changes the set commitment, and must not be usable to install a key
  the validator does not control.
- **Long-range and bootstrap trust.** Genesis-era PQ finality removes the
  classical-history forgery problem this chain would otherwise inherit, but a
  client still needs a trustworthy starting point. A checkpoint obtained from
  the same untrusted peer as the history it justifies is not an independent
  trust anchor.

The mitigations are the requirements above. None of them is evidence that the
corresponding risk is already handled in code; Section 15 states what evidence
would be.
