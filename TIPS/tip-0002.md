# TIP-0002: Post-Quantum Validator Signatures and Cryptographic Agility

## Abstract

This TIP proposes a staged transition for TOS validator authentication. TOS
will launch mainnet using its existing Ed25519 validator signatures. Neither
post-quantum (PQ) signatures nor proof aggregation is a mainnet-launch
prerequisite. Beginning in **2029**, TOS plans to introduce PQ-compatible
validator authentication through explicitly scheduled, reviewed network
upgrades, progressing from registration and shadow operation to mandatory
hybrid signatures and, subsequently, PQ-required authentication.

The design separates validator identity, signature-suite selection, signing
state, and quorum validation. It covers proposals, all Simplex vote types,
certificates, validator-key registration and rotation, and verification by
full nodes and light clients. An XMSS-family design, including leanXMSS, is a
priority candidate for evaluation, not a production algorithm selected by this
Draft. Initially, certificates carry individual signatures; leanVM-style
aggregation is a possible later, separately specified optimization.

This TIP specifies migration and safety requirements. It does **not** activate
an upgrade, allocate wire-format constructor tags, freeze a PQ parameter set,
or claim that a PQ validator implementation exists. Exact cryptographic
profiles, encodings, interoperability vectors, and activation coordinates must
be approved before enforcement. The 2029 milestone is the planned **start of
migration**, not an automatic switch, a completion deadline, or a prediction
of when quantum attacks become practical.

## Motivation

Validator signatures authorize consensus decisions. Replacing authentication
in an application wallet does not replace the signatures used to validate a
block, authenticate a voting committee, or advance consensus. TOS needs a
validator-specific migration plan that preserves operation of the mainnet it
will first launch with Ed25519.

The relevant baseline is `tosnetwork/tos` commit
`8880f99ae12634b10113f7ff0747439ed978234d`, reviewed on 2026-09-11:

- The C++ block-signature serializer writes the `ed25519_signature#5` tag,
  requires 64-byte signatures, and explicitly constructs Ed25519 validators
  for verification. It rejects duplicate and unknown signers. [1]
- Simplex supports **NotarizeVote, FinalizeVote, and SkipVote**. Its signed-vote
  decoder authenticates the serialized vote in the consensus session. [2][3]
- The Rust block codec also has fixed Ed25519 signature/public-key types. [4]
- The shared quorum predicate uses `3 * signed_weight >= 2 * total_weight`,
  with widened arithmetic and a cap on total validator weight. [5]

Consequently, this is not a BLS replacement or an application-contract change.
It affects consensus authentication, certificates, persistent signing state,
and client interoperability. A live-mainnet migration cannot silently replace
old signature bytes, reinterpret historical blocks, or rely on all clients
upgrading at once without a coordinated activation rule.

Ethereum's published roadmap motivates evaluation of hash-based validator
signatures and proof-based aggregation. [6] TOS does not inherit Ethereum's
activation decisions, parameter choices, scale assumptions, or performance
claims. In particular, the inspected leanSig implementation describes itself
as a prototype that is unaudited and not intended for production. [7]

## Normative language and maturity

MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY have the meanings defined
by RFC 2119 and RFC 8174. [12]

Normative statements in this Draft describe requirements for a future adopted
implementation. Publication or merger of this document does not change the
running network. The logical structures below are **not wire schemas**.
No client may infer constructor numbers, serialization, or an enabled PQ
suite from their illustrative field names.

A future revision or companion Core TIP must freeze the implementation-ready
profile described in Section 12. Until then, this document remains a Draft
migration specification, not a deployable consensus release.

## Specification

### 1. Scope and non-goals

This TIP covers the authentication of validator proposals; notarize,
finalize, and skip votes; vote certificates and persisted block proofs;
validator signing-key registration, rotation, and retirement; and the
signer-state requirements of stateful signature schemes. It applies to both
masterchain and shard committees, including committee transitions.

The first enforcing release MUST inventory every signature that can affect a
consensus transition, committee selection, or authenticated key replacement.
If a legacy consensus path remains enabled, that path MUST receive an equally
strong enforcing policy or be disabled at the activation boundary. Updating
only the final block-proof serializer is insufficient.

This TIP does not change stake weights, quorum thresholds, consensus voting
rules, transaction semantics, token supply, or wallet authorization. It does
not mandate a general-purpose PQ opcode or smart-contract verifier.

ADNL, overlay, transport, discovery, and encrypted-message key establishment
require a separate networking specification. They are not made PQ-secure here.
Any network envelope that is itself sufficient to authorize a consensus
transition MUST nevertheless be included in the authentication inventory.
Wallet/Agent Account migration and proof aggregation remain separate work.

### 2. Launch and migration phases

| Phase | Planned timing | Consensus authorization | Security statement |
| --- | --- | --- | --- |
| C0: Classical mainnet | Mainnet launch and initial operation | Existing Ed25519 rules and formats | Classical validator authentication |
| C1: PQ-compatible preparation | Migration begins in 2029, subject to readiness | Ed25519 remains authoritative; reviewed PQ registration and shadow verification are added | PQ-compatible, not PQ-enforced |
| C2: Hybrid required | A later, separately approved activation after C1 | The same validator supplies Ed25519 **AND** approved PQ authorization of the same statement | PQ-protected authorization under the approved hybrid profile |
| C3: PQ required | A later, separately approved activation after C2 | Approved PQ authorization is mandatory; Ed25519 is no longer an independent authority | PQ-required validator authentication, not whole-stack PQ security |

Research, implementation prototypes, audits, and isolated testnets MAY run
before 2029. They MUST NOT silently change mainnet consensus. This TIP does
not require shipping dormant PQ consensus machinery at launch.

2029 is a planning milestone. No rule is activated merely because a machine's
clock reaches 2029, and no exact activation date or block height is selected
here. Each enforcing phase requires a published profile, client releases,
operator readiness evidence, and deterministic on-chain activation
coordinates. Migration may be postponed if the gates are unmet. A material
change in the threat assessment may justify an explicitly reviewed earlier
upgrade; 2029 MUST NOT be represented as a guaranteed safe waiting period.

#### 2.1 C1 is observation, not alternative authorization

Optional PQ observations MUST NOT contribute extra voting weight or rescue
an invalid Ed25519 vote. Shadow failures MUST NOT change fork choice,
finality, or the validity of an otherwise valid classical certificate.

Shadow material SHOULD use a separately specified diagnostic channel or
sidecar rather than changing legacy signed bytes. If a PQ key registry or
other metadata changes consensus state, that change requires its own
scheduled protocol upgrade even while Ed25519 remains authoritative. Old
clients are not assumed to ignore new data safely.

#### 2.2 C2 is AND, not OR or two unrelated quorums

For an eligible validator `v` and one canonical statement `M`:

```
HybridValid(v, M) = Ed25519Valid(v, M) AND PQValid(v, M)
```

Both components MUST belong to the same validator record, role, key epoch,
policy, and statement. Two unrelated signature collections, each reaching a
quorum independently, do not establish the required intersection quorum.
An invalid required component MUST NOT be ignored, and a timeout MUST NOT
cause automatic fallback to Ed25519-only verification.

#### 2.3 C3 and subsequent algorithm changes

In C3, a valid classical signature alone MUST NOT authorize a vote, key
replacement, recovery, or policy downgrade. A profile must explicitly define
whether extra Ed25519 material is prohibited or retained solely for
non-authoritative diagnostics. It cannot become an alternative validator.

A suite replacement remains possible under the then-active authority and a
reviewed upgrade. Operational recovery from a failed PQ deployment is not a
license for a unilateral classical fallback. Any exceptional rollback
requires a separate network decision with an explicit security statement.

### 3. Policy selection and activation

The enforcing policy MUST be determined by authenticated chain state, not
peer negotiation, operator flags, local clocks, or an untrusted field in a
received vote. An activation record must identify at least:

```
ValidatorAuthPolicy (logical model)
    policy_revision
    phase
    mandatory_suite_and_parameter_profile
    signed_statement_profile
    registration_and_key_rotation_rules
    certificate_format_and_resource_limits
    masterchain_activation_coordinate
    committee_session_transition_rule
    historical_verification_rule
```

The first hybrid profile SHOULD use one mandatory PQ suite per policy to
avoid premature per-validator algorithm negotiation. Future multi-suite
policies require explicit validation and downgrade rules; cryptographic
agility does not mean arbitrary algorithms can be selected by a sender.

The policy and the complete applicable validator set MUST be cryptographically
committed to by the signed context. The existing short validator-set hash
alone MUST NOT serve as the new security commitment. The activation profile
must select the full commitment construction and assess its security.

Policy changes take effect at announced masterchain and committee/session
boundaries. The activation specification MUST define old in-flight sessions,
shard split/merge behavior, parent certificates, and committee handovers.
An old-format certificate may be accepted as historical evidence where the
profile permits it; it MUST NOT authorize a new-policy duty by being replayed
across a boundary. Historical verification selects the policy that governed
the signed duty, not simply the latest local configuration.

Before C2, the selected enforcing committee MUST have valid required key
records for every included validator. Selection and eligibility changes must
be explicit and finalized in advance. Nodes MUST NOT silently drop
unregistered/offline validators and recompute the denominator of a current
committee. Readiness must be assessed for each affected shard committee,
not just by counting PQ-enabled nodes globally.

### 4. Validator identity, keys, and suites

Validator identity and stake accounting MUST be separable from the current
signature algorithm. A legacy identifier may remain a lookup key, but
possession of its old Ed25519 private key MUST NOT remain an implicit recovery
authority after strict PQ enforcement.

A logical signing-key descriptor contains:

```
ValidatorSigningKey
    validator_identity
    role
    suite_id
    parameter_profile_id
    public_key_bytes
    key_epoch
    validity_domain
    stateful_capacity_or_schedule   # when applicable
```

Suite identifiers bind an exact algorithm, parameter set, key/signature
encoding, verification behavior, domain/prehash rules, and resource limits.
Unknown, retired, or non-enabled suites MUST fail closed in enforcing paths.
A recognized algorithm name without an approved parameter profile is not a
valid suite. PQ public keys MUST NOT be assumed to be 32 bytes or represented
only by a 256-bit Merkle root when the scheme requires additional material.

Proposal signing, consensus votes, and administrative key changes MUST have
separate roles and domains. Stateful schemes MUST additionally ensure that
role separation never aliases the same one-time signing capacity. Separate
proposal and vote roots are the preferred starting point for evaluation;
separate vote-type roots or a proven disjoint allocation are also possible.
Network keys are distinct from consensus signing keys.

#### 4.1 Registration and proof of possession

Registration MUST bind the validator identity, stake/registry record, role,
suite, full public key, key epoch, network, and effective validity interval.
The owner/registry authorization required by the current policy and proof
of possession of the new key are both required. A PQ proof of possession
alone does not prove ownership of an existing validator's stake.

For stateful keys, proof of possession itself consumes signing capacity. It
MUST use a reserved, non-overlapping duty and the same crash-safe signer
rules as ordinary signatures. Registration is finalized before the new key
may contribute consensus weight.

#### 4.2 Rotation, retirement, and administration

Rotation MUST be authorized under the current enforcing policy and include
proof of possession of the replacement key. Epochs advance monotonically;
relabeling a used stateful key with a new epoch MUST NOT reset its capacity.
Reactivation of the same key material must not reopen retired leaves.

Rotation becomes effective at an explicit boundary; delayed messages are
verified with the key valid for their duty. Old public keys and profile
metadata remain available for historical verification. Retired secret
material SHOULD be destroyed subject to the reviewed backup design.

During C2/C3, key-registration, election/configuration, recovery, and policy
administration paths MUST NOT permit an Ed25519-only actor to restore weaker
validator authority. These dependencies are enforcement gates, even if their
implementation is spread across additional contracts or TIPs. Ordinary
wallet and stake-withdrawal authentication remain separately scoped; this
TIP does not by itself make validator funds PQ-safe.

### 5. Canonical signed statement and serialization

The activation profile MUST define one canonical consensus statement that
both hybrid components authenticate. The logical context includes:

```
ConsensusStatement
    domain_and_statement_version
    network_global_id_and_genesis_commitment
    policy_commitment
    complete_validator_set_commitment
    validator_identity_and_key_binding
    workchain_and_shard
    session_identifier
    role_and_vote_type
    consensus_position
    exact_payload_commitment
```

The exact profile must cover proposals, NotarizeVote, FinalizeVote, SkipVote,
and any other enabled consensus-authorizing duty. Payload semantics are
typed: a skip vote is not an empty finalize vote. Existing consensus rules
about permitted combinations of votes MUST be preserved, not reinvented by
the signature layer. Any attempt/round/sub-duty dimension actually present
in the implementation must be accounted for.

A hybrid signer MUST NOT simply sign the old vote with Ed25519 and a
differently scoped wrapper with PQ. Algorithm-specific domain processing
may differ only as specified by the profile, while committing both
components to the identical canonical statement and complete key/policy
binding. JSON, ambiguous concatenation, or hash truncation is not a wire
specification.

New TL/TL-B constructors and all dependent codecs require an explicit
versioned format. Existing Ed25519 constructor tags retain their historical
meaning. The future release must fix lengths, endianness, canonical
encodings, cell layout, maximum chain depth, count limits, and rejection of
trailing or duplicate data. Large PQ material must not be squeezed into a
single cell or an existing 64-byte signature field.

### 6. Certificates and quorum accounting

The first enforcing deployment uses **individual raw PQ or paired hybrid
signatures**. It MUST NOT depend on a leanVM prover to produce or finalize
blocks. Certificate generation and verification must cover live consensus,
block proofs, catch-up, and light-client interfaces.

For a well-formed certificate, a validator contributes its recorded stake
weight once only after its required authentication succeeds. Duplicate or
unknown signers, wrong key epochs, mismatched statements, and invalid
required components are rejected. Weight is taken from the authenticated
validator set, never a sender-supplied total.

This TIP does not alter the existing quorum predicate. For a nonempty,
valid set with total weight `W`, let `S` be the sum of weights of distinct,
fully authenticated signers. The current baseline requires:

```
3 * S >= 2 * W
```

Arithmetic MUST be checked or widened and must preserve the existing weight
bounds. In hybrid mode, `S` counts only validators whose **two** components
pass. `S_ed >= quorum` and `S_pq >= quorum` are not substitutes.

The activation profile MUST impose exact public-key, signature, certificate,
proof, and decode-allocation bounds. Reject unsupported suite/profile IDs
and excessive lengths before expensive verification. Benchmark adversarial
traffic, not just valid signatures. A voting-weight readiness percentage
is an operational gate, not a new quorum denominator or safety theorem.

### 7. PQ profile selection

**leanXMSS / XMSS-family signatures are priority research candidates, not
mandatory production suites in this Draft.** NIST SP 800-208 and RFC 8391
provide references for standardized stateful hash-based schemes. [8][9]
An XMSS-like research implementation is not automatically byte-compatible
with RFC 8391 or covered by NIST's approved profiles.

The evaluation must compare the chosen hash-based candidate with suitable
stateless alternatives, including ML-DSA and SLH-DSA. [10][11] It must consider
security analysis, multi-target exposure, key generation, preparation,
signing/verification latency, public-key and signature sizes, lifetime,
failure recovery, implementation diversity, and validator operating cost.

Before adoption, a profile MUST pin exact algorithm and parameter definitions,
reference revisions and test vectors, key generation and RNG requirements,
message preprocessing, verification/canonicality rules, and the applicable
security target. Hash choices in the signature, statement, key/set
commitments, and any later proof system must be assessed together. There is
no blanket claim that every 256-bit hash construction provides the same
post-quantum security margin.

A moving upstream branch, an algorithm brand name, or a benchmark on a
different blockchain cannot serve as a normative cryptographic profile.
An audited, interoperable alternative may be selected in 2029 or later
without abandoning this TIP's migration architecture.

### 8. Stateful signing requirements

These requirements apply if the selected suite uses one-time signing
capacity. Stateless suites still need consensus anti-equivocation controls.

#### 8.1 Allocation domain

For every actual stateful public key, allocation MUST be unique across all
roles, sessions, committees, shards, restarts, failover instances, registration
proofs, and administrative signatures that use that key. A logical
`key_epoch` label alone cannot create fresh cryptographic capacity.

A naive `leaf = slot * 2 + vote_type` is **not** an approved schedule. It omits
SkipVote, does not address session-local slot resets or concurrent shards,
and does not prove that each assigned duty can sign at most one statement.
A synchronized profile must provide an injective duty-to-capacity mapping,
its permitted retries, bounds, and rollover behavior. A sequential allocator
is another possible profile, but it still requires anti-equivocation rules.

Changing candidate hashes or adding a domain label does not make reuse of
the same one-time key safe. Candidate-dependent allocation MUST NOT be used
to evade consensus double-signing restrictions. Proving signature-state
uniqueness and enforcing consensus voting rules are separate obligations.

#### 8.2 Persist before signing; fence concurrent instances

The authoritative signer MUST validate the request and durably reserve the
capacity, exact statement, and relevant anti-equivocation record **before**
invoking the signature operation. It must persist a successful signature
before releasing it to callers. Retransmission returns the stored identical
signature; it does not invoke the stateful primitive again for that duty.

A crash after reservation cannot free the capacity. Recovery may return a
fully committed cached signature. When completion is uncertain, the affected
capacity remains consumed and the signer must fail closed or follow the
profile's explicitly safe advance/rekey procedure. It must not guess from
absence in the chain that a signature was never exposed.

Only one fenced writer may allocate for a key at a time. Redundant validators
need a reviewed single-authority or coordinated signing design; copying a
keystore to two machines is not redundancy protection. Restoring a VM/disk
snapshot must not roll back allocation or consensus anti-equivocation state.

Signer state MUST be logically separated from prunable consensus-session
storage. Session garbage collection, chain reorganization, and database
cleanup must not reset consumed capacity. A conservative lifetime record or
non-rollbackable high-watermark must survive for every key that could still
be restored. Deleting records is allowed only under a reviewed retirement
policy that also prevents reuse of the corresponding secret.

#### 8.3 Exhaustion, preparation, and recovery

The profile must bound signing capacity per key and per deployment, including
worst-case skip/proposal/admin duties, retries, and concurrency. Operators
need measurable reserve thresholds and a rotation lead time. Key preparation
must keep up with the actual schedule. Counter overflow, exhausted capacity,
missing authoritative state, or an unverifiable backup MUST stop signing;
none permits fallback to a traditional key.

Storage fault injection, active/active races, snapshot rollback, and recovery
from partial writes are release-blocking tests. A double-sign penalty after
the fact is not a substitute for preventing state reuse.

### 9. Aggregation and networking boundaries

A subsequent TIP MAY introduce leanVM-style or other PQ-sound aggregation
after raw-signature deployments establish a measured need. Such a TIP must
specify the proof system, exact security parameters, statement binding,
signer uniqueness, weight accounting, verifier resources, data availability,
and failure handling. Proving classical signatures alone does not convert
them into PQ signatures.

A future proof producer must not gain voting weight by producing a proof.
If proof generation is moved off the finality path, clients need a complete,
validated raw-certificate path rather than a weaker fallback. If proofs are
mandatory on that path, withholding/latency becomes a liveness dependency
that must be budgeted. This Draft makes neither design choice mandatory.

Classical network identities may remain during the scoped transition only
with an explicit threat analysis. Compromised transport identities may enable
impersonation, eclipse, replay, or denial of service. A retained transport
credential MUST NOT independently authorize a consensus vote. This TIP
claims no PQ confidentiality, PQ transport authentication, or guaranteed
network liveness against quantum-capable attackers.

### 10. Historical verification and long-range security

New verification code MUST retain the exact historical Ed25519 rules for
pre-activation data. Historical authenticity is not repaired simply by
wrapping old signatures in a new proof or changing a type tag.

Before enforcement, the activation specification must define an authenticated
transition checkpoint binding the predecessor chain state, validator set,
and new policy. It must explain how continuously verifying nodes cross the
boundary and how new or long-offline nodes obtain a trusted checkpoint and
verify later committee transitions.

The first transition is necessarily rooted in the authority in force before
it. Bootstrapping from a fully forged classical history is not prevented by
this TIP alone if classical keys are already breakable. Checkpoint
publication, weak-subjectivity/trust assumptions, and protection of the
transition itself must be explicit; a checkpoint selected from the same
untrusted peer as the alleged history is not an independent trust anchor.

Light clients, bridges, indexers, archives, and validator recovery tools must
understand the correct certificate era. Bridges with embedded verifiers need
their own coordinated deployment and activation checks, not just a node
binary update. This TIP does not reset genesis or rewrite mainnet history.

### 11. Implementation boundaries and delivery sequence

Normative rules belong in this TIP and its reviewed profile/activation
revisions. Reference implementation, profiling, CI, and operator tooling
belong in `tosnetwork/tos`, linked to a pinned TIP revision.

| Boundary | Work to audit and implement |
| --- | --- |
| Validator registry, election, configuration, zerostate | Key ownership, suite/epoch binding, committee eligibility, activation and recovery authority |
| `keys/`, `keyring/`, `validator-engine/` | Typed signer interfaces, PQ key lifecycle, persistent allocation, failover and administration |
| `validator/consensus/`, including `simplex/votes.*` | Proposals, all vote types, certificates, duty binding, anti-equivocation and session transitions |
| `crypto/block/signature-set.*` and protocol schemas | New typed signatures, bounded serialization, historical proof verification |
| `tosctl/src/block/src/signature.rs` and other clients | Matching codecs and verifier behavior, light-client and bridge integration |
| Consensus and operator tests | Deterministic vectors, differential verification, crash/fault tests and measured overhead |

This is a work inventory, not a claim that each boundary already supports PQ.
The initial implementation must audit all callers rather than treating the
Rust codec as the only production consensus path.

The intended sequence is: preserve classical launch; prototype and benchmark;
freeze a candidate profile; rehearse registration and shadow operation;
review a 2029-or-later C1 upgrade; validate hybrid interoperability and
recovery; activate C2 at announced coordinates; and only later consider C3.
Stages may span multiple releases and years. No production cutover is
implied by merging a prototype or this document.

### 12. Activation and Final-status gates

Before an enforcing profile can be activated, the following must be complete:

1. An exact cryptographic profile and canonical TL/TL-B/wire formats, including
   constructor tags, duty mappings, size limits and suite registry semantics.
2. Reviewed registration, rotation, election, governance/recovery, and
   transition-checkpoint rules with no classical bypass of strict authority.
3. Known-answer signature vectors and negative vectors, cross-language codec
   agreement, and at least two independently exercised verifier implementations.
4. Security review of the scheme, its integration, and any stateful signer;
   no unresolved correctness or key-reuse blockers.
5. Multi-node masterchain/shard tests covering loss, reordering, partitions,
   committee transitions, failover, rollback, and exhausted keys.
6. Published CPU/memory/bandwidth/latency results on specified hardware, at
   representative committee sizes and under invalid-input load. The upgrade
   must adopt numerical acceptance budgets rather than inventing them here.
7. Operator migration and recovery rehearsals, client/bridge readiness,
   announcement/lead-time policy, and deterministic activation coordinates.

C0 mainnet launch does not depend on those future gates. C2/C3 do.
If gates are unmet, remain in the preceding approved phase; do not weaken
verification to meet the calendar. This TIP must not be marked Final as an
implemented PQ standard while its cryptographic profile, encoding, activation
rules, and consensus conformance evidence remain unspecified.

## Rationale

**Ed25519 first.** The migration is intentionally separate from launch. It
allows ordinary mainnet operation while future algorithms, tooling and
operational experience mature, without implying classical cryptography is
safe until a known date.

**Hybrid before PQ-required.** Per-validator AND authorization preserves the
classical check while requiring the new proof of authority. It provides an
explicit evaluation and deployment step, not an OR escape hatch. The complete
hybrid construction still needs integration analysis; concatenating arbitrary
signatures is not a security proof.

**Cryptographic agility without premature algorithm selection.** Pinning
role, suite, parameters and epochs makes later changes explicit. Keeping
leanXMSS a priority candidate avoids treating a research library as an
audited 2029 dependency. Stateless candidates offer a meaningful comparison
because signer recovery is part of system safety, not an implementation detail.

**Raw signatures first.** TOS currently verifies sets of individual Ed25519
signatures. [1][4] Direct PQ verification is the simplest baseline against
which to measure bandwidth and latency. Aggregation can be evaluated later;
it must not be assumed necessary or fast enough without TOS measurements.

**Protocol and operations together.** A validator-key change affects signing
processes, stored proofs, trusted checkpoints, election/administration and
network authorization boundaries. Omitting any of these may preserve a
classical bypass despite a correct PQ verification function.

## Backwards Compatibility

The C0 launch remains Ed25519-only under existing rules. This proposal does
not demand changes to launch keystores, addresses, signatures or block formats.

After launch, registry changes, new signature encodings and mandatory PQ
checks are protocol upgrades. Depending on the final design they require
hard-fork-style client coordination; they MUST NOT be advertised as a
transparent library swap. Existing validators and service operators receive
published migration procedures before an enforcing transition.

Upgraded clients retain historical verification. Unupgraded clients cannot
be assumed to validate new-era certificates, even if a hybrid certificate
contains an Ed25519 component. They must stop at or explicitly report the
unsupported boundary rather than claim full validation by ignoring PQ rules.

No token migration, genesis reset, wallet version bump, or stake-weight
change is mandated. Wallet and Agent Account authentication changes neither
satisfy nor depend on the validator transition described here.

## Test Cases

### Included policy-model cases

[`../assets/tip-0002/policy-cases.json`](../assets/tip-0002/policy-cases.json)
contains input/expected-output cases for phase authorization and weighted
certificates. [`check-policy.py`](../assets/tip-0002/check-policy.py) is a
standard-library-only executable model of those rules:

```
python3 assets/tip-0002/check-policy.py
```

The `ed_valid` and `pq_valid` fields are **supplied verification outcomes**,
not signatures. The model tests AND authorization, signer uniqueness,
registry/context gating and the existing quorum arithmetic. It is not a
cryptographic verifier, a TOS consensus implementation, or evidence of PQ
performance. Its shadow mode models consensus validity only, not diagnostic
handling. Removing the AND condition must make the negative corpus fail.

### Required consensus and signer conformance cases

| Input or injected condition | Required outcome |
| --- | --- |
| Valid legacy certificate before activation | Verify under the historical Ed25519 rules |
| Ed25519-only vote in hybrid-required era | Reject; no PQ timeout fallback |
| Ed25519 and PQ quorums with insufficient common signer weight | Reject |
| Three equal-weight validators, two fully authenticated signers | Pass the baseline `>= 2/3` predicate |
| Duplicate signer, unknown signer, or sender-supplied inflated weight | Reject |
| Changed network/genesis, policy, committee, role, payload or key epoch | Reject the mismatched authorization |
| Notarize signature presented as finalize or skip authorization | Reject |
| Wrong suite, parameters, malformed/trailing bytes, excessive size/depth | Reject deterministically within resource bounds |
| Valid signature under a retired key for a current duty | Reject; historical acceptance does not confer current authority |
| Current PQ policy with classical-only recovery/registration authorization | Reject |
| Session reset or concurrent shard duty aliases one-time capacity | Signer refuses; allocation profile/test fails |
| Registration proof overlaps a consensus-signing leaf | Signer refuses; profile is invalid |
| Crash after reservation, before signature persistence | Do not reclaim capacity or sign again speculatively |
| Completed request retransmitted | Return cached signature; no second primitive invocation |
| Restored old snapshot or two active allocators for the same key | Fence/refuse unsafe signer; no duplicate allocation |
| Exhausted key, counter overflow, lost signer state | Stop signing and use the approved recovery/rotation procedure |
| Consensus-session storage garbage collection | Preserve signer non-reuse and anti-equivocation protection |
| Activation with an unregistered selected validator | Reject invalid committee/activation state; do not renormalize weights |
| Shard session straddles the policy boundary | Use the frozen transition rule; no local-clock choice |
| Fabricated classical ancestry supplied to a new client | Do not claim trustless PQ bootstrapping without an approved anchor |

Byte-level codec and real PQ known-answer tests are intentionally unassigned
until a suite/profile is selected. They are mandatory before activation and
must be added as versioned assets or linked pinned implementation tests.
Test descriptions and the Boolean model MUST NOT be substituted for them.

## Reference Implementation

There is **no production PQ validator reference implementation supplied by
this TIP**. The baseline source links [1]-[5] identify existing boundaries,
not completed modifications. The included policy checker is an illustrative
conformance aid only. Future implementation PRs must identify this TIP's
revision, selected profile, actual tests and measured results.

The upstream leanSig project [7] is a candidate research reference, not a
production dependency or a TOS reference implementation. leanVM-style
aggregation is discussed as related work [6], not required by C1/C2/C3.

## Security Considerations

The transition aims to protect validator authorization, conditional on the
selected profile, key integrity and underlying consensus assumptions. It
does not prove the entire chain, wallets, network, or historical bootstrap
quantum-safe.

Primary risks are a weak/incorrectly integrated PQ suite; inconsistent
canonical encoding; cross-role/network/key replay; double-counted stake;
AND-to-OR downgrade; classical key-registration or governance bypass;
one-time-key reuse; exhaustion and unsafe recovery; expensive malformed
certificates; and long-range attacks against classical history.

The mitigations are the requirements above, not a claim that these risks are
already resolved in code. In particular, mere registration of PQ keys and
successful shadow verification provide readiness information, not PQ-enforced
consensus. Generic hashes and optional proof systems need their own security
analysis, and keeping a classical transport layer retains availability and
identity risks outside the scoped signature claim.

The calendar is not a cryptographic assumption. TOS must continue reviewing
threat evidence before and after 2029 and use explicit network decisions for
acceleration, postponement, or an emergency response.
